      "body": "# SEP: securitySchemes in Tool Metadata for Mixed-Auth Servers\n\nAuthors: Duke Kim (duke@openai.com), Thiago Hirai (thiago@openai.com)\nStatus: Draft\nSponsor: Nick Cooper (nickc@openai.com)\nType: Standards Track\nCreated: 2025-09-17\n\n## Summary\nWe propose adding an optional securitySchemes field to MCP tool descriptors. This makes it possible for a server to mark which tools are open to everyone and which need auth. Clients can then:\n- Show clear UI labels (e.g. “Public” vs. “Requires sign-in”).\n- Ask users to sign in before calling protected tools.\n- Pick between public and authenticated versions of the same tool.\n\nThis is a small, backward-compatible change. For now, we support just two scheme types:\n- \"noauth\" → tool can be called without credentials\n- \"oauth2\" → tool needs OAuth 2.0 (with optional scopes list)\n\nMore scheme types can be added later without changing the shape of the field.\n\n## Motivation\nRight now, clients only discover auth needs by trying and failing, or by reading docs. This isn’t great.\nBy declaring securitySchemes per tool, servers can:\n- Improve UX: Clients know upfront if a tool is public or needs auth.\n- Guide flows: Clients can prompt users for login before invoking a protected tool.\n- Reduce mistakes: Servers can mark tools as public vs. protected.\n- Stay flexible: Easy to add new auth schemes (API keys, mTLS, etc.) later. \n\n## Design\n### Tool Descriptor Change\nEach tool can include a new optional securitySchemes field in its tools/list response:\n```\n{\n  \"name\": \"get_weather\",\n  \"title\": \"Weather Info\",\n  \"description\": \"Get current weather for a location\",\n  \"inputSchema\": {\n    \"type\": \"object\",\n    \"properties\": { \"location\": { \"type\": \"string\" } },\n    \"required\": [\"location\"]\n  },\n  \"securitySchemes\": [\n    { \"type\": \"noauth\" },\n    { \"type\": \"oauth2\", \"scopes\": [\"weather.read\"] }\n  ]\n}\n```\n\n### Field Definition\n`securitySchemes` (array, optional)\n- If missing → tool follows the server’s default policy.\n- If empty array → discouraged, same as missing.\n- If present with entries → lists supported auth schemes.\n\n#### Scheme types (so far):\n- noauth: no credentials required.\n- oauth2: needs OAuth2; can list scopes if relevant.\n\n### Multiple Schemes\n- Tools can list both noauth and oauth2 to mean “works anonymously, but auth gives more features.”\n- Clients can pick any scheme they can satisfy, usually preferring authenticated.\n- Servers must enforce auth rules regardless of client metadata.\n\n## Examples\n**Public with optional auth**:\n```\n{\n  \"name\": \"search\",\n  \"title\": \"Public Search\",\n  \"description\": \"Search public documents.\",\n  \"inputSchema\": { \"type\": \"object\", \"properties\": { \"q\": { \"type\": \"string\" } }, \"required\": [\"q\"] },\n  \"securitySchemes\": [\n    { \"type\": \"noauth\" },\n    { \"type\": \"oauth2\", \"scopes\": [\"search.read\"] }\n  ]\n}\n```\n\n**Auth required**:\n```\n{\n  \"name\": \"create_doc\",\n  \"title\": \"Create Document\",\n  \"description\": \"Make a new doc in your account.\",\n  \"inputSchema\": { \"type\": \"object\", \"properties\": { \"title\": { \"type\": \"string\" } }, \"required\": [\"title\"] },\n  \"securitySchemes\": [\n    { \"type\": \"oauth2\", \"scopes\": [\"docs.write\"] }\n  ]\n}\n```\n\n**No field (inherits server policy)**:\n```\n{\n  \"name\": \"status\",\n  \"title\": \"Server Status\",\n  \"description\": \"Basic health info.\",\n  \"inputSchema\": { \"type\": \"object\", \"properties\": {} }\n}\n\n```\n\n## JSON Schema (informative)\n```\n{\n  \"$id\": \"https://modelcontextprotocol.io/schemas/tool.securitySchemes.v1\",\n  \"type\": \"object\",\n  \"properties\": {\n    \"securitySchemes\": {\n      \"type\": \"array\",\n      \"items\": {\n        \"oneOf\": [\n          { \"type\": \"object\", \"required\": [\"type\"], \"properties\": { \"type\": { \"const\": \"noauth\" } } },\n          { \"type\": \"object\", \"required\": [\"type\"], \"properties\": {\n              \"type\": { \"const\": \"oauth2\" },\n              \"scopes\": { \"type\": \"array\", \"items\": { \"type\": \"string\", \"minLength\": 1 }, \"uniqueItems\": true }\n            }\n          }\n        ]\n      }\n    }\n  },\n  \"additionalProperties\": true\n}\n\n```\n\n## Compatibility\n- **Optional field** → no breaking changes.\n- Old clients ignore it and keep using runtime errors/docs to figure out auth.\n- Old servers just don’t send it.\n\n## Security Notes\n- Declaring `noauth` makes public tools explicit and auditable.\n- Declaring `oauth2` with scopes helps clients request the right tokens.\n- This field is just metadata; servers still must enforce auth.\n- Misconfigurations (e.g. forgetting to require auth) are the main risk.\n",

      "body": "The Output Schema section says servers **MUST** return structured results that conform to the schema, and clients **SHOULD** validate them against it. It doesn't say which schema applies when the two sides hold different versions. Clients cache tool lists, so after a server changes a tool, a client can validate a new result against the old schema.\n\nWhat happened to us: our server removed two fields that a tool's `outputSchema` had marked required. A Claude Code session and ChatGPT both still held the old schema, and both rejected every result from that tool until they reconnected. The results were valid against the current schema the whole time. ChatGPT also kept the old tool list until the user pressed \"Refresh tools\" in its settings.\n\n`notifications/tools/list_changed` doesn't close the gap. It only helps clients that listen for it, and a call can still arrive before the refresh.\n\nProposed non-normative note under Output Schema:\n\n> Clients may hold a cached copy of a tool's `outputSchema`. To change it without breaking them, servers SHOULD only add optional properties. Removing, renaming or narrowing a property, or making one required, can cause clients holding the earlier schema to reject valid results. To replace a property, add the new one and keep the old one until clients have refreshed.\n\nOpen question: should a client refetch `tools/list` before treating a result that fails validation as a server error?\n\nI'm happy to open a docs PR with this wording.       "body": "# Proposal: governed workflow execution contract (runbook.v1)\n\n**Status:** Proposal for discussion\n**Reference implementation:** https://github.com/CorpusIQ/runbook-spec\n**Conformance:** 24/24 tests passing\n\n## Summary\n\nMCP servers can expose a tool or workflow, but the model still decides whether to invoke it and how completely to follow it. For enterprise workflows (financial reporting, compliance, reproducible analytics, product actions), execution must be required, versioned, and auditable. This proposal defines an application-layer contract for that: **runbook.v1**.\n\n## The core idea\n\nA runbook is a versioned manifest resolved from a trusted skills server and executed by the host with fail-closed semantics:\n\n```json\n{\n  \"runbook_id\": \"executive-snapshot\",\n  \"version\": \"4.2.0\",\n  \"mode\": \"required\",\n  \"failure_policy\": \"fail_closed\",\n  \"allowed_tools\": [\"quickbooks_profit_and_loss\", \"stripe_revenue\", \"ga4_sessions\"],\n  \"checkpoints\": [\n    {\"id\": \"cp-revenue-qb\", \"kind\": \"tool_call\", \"required\": true,\n     \"match\": {\"tool\": \"quickbooks_profit_and_loss\"}},\n    {\"id\": \"cp-emit\", \"kind\": \"condition\", \"required\": true,\n     \"condition\": \"final_output\"}\n  ],\n  \"completion\": {\"condition\": \"final_output\", \"receipt\": true}\n}\n```\n\n## Design principles\n\n1. **Acquisition is deterministic.** The host resolves by ID + version from a trusted skills server. No semantic search. Content hash, schema, and prerequisites validated before the first model call.\n2. **Version pinning is absolute.** The exact version is bound for the life of the run, in a host-controlled instruction layer, not pasted into chat as untrusted prose.\n3. **Tool surface is an allow-list.** The model only sees and calls declared tools.\n4. **Checkpoints are observed, not self-reported.** The host derives checkpoint state from the tool-call stream.\n5. **Completion is host-evaluated** with a machine-readable receipt: runbook_id, version, content_hash, tools_called, checkpoint_states, result_summary, failure_reason.\n6. **Required mode is never silently downgraded.** If the host cannot honor the contract, it returns `runbook_failed` instead of a normal answer.\n\n## Why it does not change MCP\n\n- The manifest resolves through existing MCP resources.\n- Enforcement is host-side.\n- The closest existing primitive is `tool_choice` forcing, which proves forced selection is practical but covers one bounded call. A runbook governs multiple turns and multiple connector calls, which is why the contract lives in the host loop rather than a single API request.\n\n## Non-goals\n\n- No change to the MCP transport protocol.\n- No server-side execution model.\n- No model polling of status (non-deterministic by design).\n\n## What we are offering\n\n- Full schema: schema/runbook.v1.schema.json\n- Specification: spec/runbook-v1.md\n- Reference host implementation (Python, against the Messages API): reference/python/runbook_host.py\n- Conformance suite: conformance/run_conformance.py (24/24 passing)\n- Real-world example: examples/executive-snapshot.json\n- Real customer scenarios available on request\n\n## Questions for the community\n\n1.       "body": "## Summary\r\n\r\nThis SEP proposes **Tool Manifests**: two coordination primitives that let a client obtain and keep current a server's tool definitions incrementally rather than wholesale.\r\n\r\n- **`tools/manifest`** returns, for every tool the session may see, a compact entry: name, title, a server-computed `digest` and byte `size` of the full definition, and optional annotations. No schemas.\r\n- **`tools/describe`** returns the complete `Tool` definitions for an explicitly named subset, batched into one round trip.\r\n- **`tools.manifest`** is a single server capability advertising both.\r\n\r\n`tools/list` is unchanged and remains the compatibility floor. The manifest and `tools/list` MUST return the same set of tools for a session, and every name in the manifest MUST be describable. The digest is computed over the entire `Tool` under a defined canonical serialization (RFC 8785), so a client reconciles a cache by comparing digests and refetching only what changed.\r\n\r\n## Motivation and Context\r\n\r\nThis SEP makes no claim about model context tokens. How a host places definitions in front of a model is a host concern, already addressed by client-side progressive discovery (documented in the client best-practices guide) and by native provider tool search. This SEP addresses the step before that: how a client, or an intermediary acting for many clients, acquires the definitions those mechanisms depend on and learns which ones changed.\r\n\r\nToday the protocol offers one way to obtain definitions: `tools/list`, which returns everything with full schemas every time. That is adequate for dozens of tools and breaks in two situations that are now common:\r\n\r\n- **Catalogs too large to fetch wholesale.** Servers fronting an entire product surface, and aggregators fronting many upstream servers, expose hundreds to thousands of tools. Every cold start and reconnect pulls every definition, most of it unchanged since last time. There is no way to ask for three named tools.\r\n- **Catalogs that change while cached.** `notifications/tools/list_changed` says something changed but not what. The SEP-2549 TTL says how long to trust a result but not which entries went stale. A client with a thousand cached definitions refetches a thousand to learn that one moved.\r\n\r\nImplementations that hit these limits have each built the same shape privately: a lightweight index entry, a fetch of the full definition by identifier, invocation by that identifier. Tool aggregators and domain-grouped servers are public examples. Because each layer defines its own contract, tools discovered through it arrive at the host as result data behind a generic wrapper tool. The host cannot register them natively with the model provider, cannot read their annotations before inspecting them, and cannot apply per-tool policy. A standard shape fixes both edges of that problem.\r\n\r\n## What This SEP Proposes\r\n\r\n- New method **`tools/manifest`** returning `ToolManifestEntry[]` with `name`, optional `title`, required `digest` in the form `sha256:<hex>`, required `size` (byte length of the canonical serialization the digest covers), and optional `annotations`. The result reuses the SEP-2549 `CacheableResult` fields.\r\n- New method **`tools/describe`** returning full `Tool[]` for named tools, order-preserving, with an implementation-defined batch bound. Unknown names return `-32602` with `data.unknownNames`, following SEP-2164.\r\n- New server capability **`tools.manifest: boolean`**.\r\n- A stated **criterion for entry contents**: what a client needs to decide whether to fetch and to tell whether a cached copy is current, and nothing it needs to use the tool. This is the deliberate opposite of SEP-2640's complete skill entries, for the reason that a tool's definition is the payload.\r\n- A defined **reconciliation procedure** (manifest, compare digests, drop removed names, describe changed names in size-budgeted batches, verify) and a statement of how the digest, the change notification, and the SEP-2549 TTL divide the work.\r\n- **Extension points**: extensions may add optional fields to the manifest entry, and metadata stored under a namespaced key in a tool's `_meta` is covered by the digest and gets change detection for free. This is designed so the Primitive Grouping IG's work can layer onto the manifest rather than compete with it.\r\n- **`tools/list` unchanged.** A trivial polyfill derives both methods from any existing `tools/list` implementation.\r\n\r\nRemoved since the original draft: the `query` parameter (SEP-1821's territory), the required `summary` and `tags` fields (discovery metadata, left to the grouping work), and the custom `-32002` error code.\r\n\r\n## How Has This Been Tested?\r\n\r\nA reference prototype exists on a branch of the TypeScript SDK fork:\r\n\r\n- **Fork branch**: [`SylonZero/typescript-sdk@sep/progressive-tool-disclosure`](https://github.com/SylonZero/typescript-sdk/tree/sep/progressive-tool-disclosure/examples/progressive-disclosure)\r\n\r\nThe prototype predates this revision. It implements the same two-method shape and the same canonical-JSON digest under the earlier names, plus the surfaces this revision removed. The SEP's Reference Implementation section marks each item that the update will change. It is being reworked against a production harness, and the wire-cost benchmark specified in the SEP's Performance Implications section (bytes, definitions, and round trips at cold start and after 1, 10, and 100 changes on a 1,000-tool synthetic server) will replace the token benchmark. Values in that table are placeholders until it runs.\r\n\r\nThe existing 35 tests cover canonical serialization, digest stability under key reordering, change detection on mutation, pagination, batch bounds, unknown-name rejection, and cache reconciliation. The SEP's Testing Plan lists the additions required for this revision.\r\n\r\n## Relationship to Other SEPs\r\n\r\n- **SEP-2640 (Skills Extension)**: precedent. Its `skills/list` entries carry `sha256:` digests and byte sizes for lazily fetched content, reuse the SEP-2549 cache fields with the same freshness-not-integrity framing, use `-32602` for unknown items, and treat a digest match as consistency rather than trust. This SEP adopts the same digest format, size pairing, cache fields, error code, and security framing deliberately, so a host implementing both handles one pattern.\r\n- **SEP-2549 (TTL for List Results)**: complementary; the manifest result reuses its fields.\r\n- **SEP-2164 (Resource Not Found Error)**: followed for unknown-name errors.\r\n- **SEP-1821 (Dynamic Tool Discovery)**: orthogonal; this SEP carries no query surface.\r\n- **SEP-1862 (Tool Resolution)**, **SEP-1881 (Scope-Filtered Discovery)**, **SEP-2564 (Server-Side Filtering)**: orthogonal or compatible, as described in the SEP.\r\n- **Primitive Grouping IG**: this SEP is positioned as the retrieval substrate under that group's organization strategies, with explicit extension points for it.\r\n\r\n## Breaking Changes\r\n\r\n**None.** Servers that do not advertise `tools.manifest` are unaffected.
