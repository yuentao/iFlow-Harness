目标是让「执行命令」工具卡在长驻命令运行期间实时显示输出，而不是等命令结束才一次性出现。

已定位根因（bundle 逐行实证，CLI 0.5.19-custom.12）：
- `ShellTool.execute(e, r, n, o)` 的第 3 参就是增量输出回调，CLI 内部已按 1s 节流推送累计 stdout/stderr；交互 TUI 走 `tool.canUpdateOutput && outputUpdateHandler` 接线（iflow.readable.js:147136）。
- ACP 主会话的 `AcpSession.runTool()` 调用 `m.execute({callId, …args}, signal)` 时**没传第 3 参**（iflow.readable.js:209653），且只在结束时发一条 `tool_call_update(completed)`——所以面板全程看不到输出。

实施步骤：
1. CLI 侧（iflow-fork，唯一执行体）：在 `reverse/iflow.readable.js` 的 `runTool()` 给 execute 传入增量回调；`canUpdateOutput` 工具（即 run_shell_command）每收到一次累计输出就发 `tool_call_update(status:"in_progress", content:[…])`，只保留末尾 6000 字符；用 Promise 链串行化并让 completed/failed 更新等待该链，避免状态回退；`IFLOW_LIVE_OUTPUT=0|false` 可关闭。随后用 esbuild 重建 `bundle/iflow.js`（已实测重建体积与现 bundle 仅差 1 字节，命令可靠）。
2. 刷新 harness 内置 CLI：`npm run vendor:cli -- --force`（从本地 fork 拷贝并裁剪）。
3. Host reducer（`shared/session-state.ts`）：保留现有「新 output 覆盖旧 output」的增量合并语义，并加终态保护——completed/failed 之后迟到的 in_progress 帧不得把卡片状态打回执行中。
4. Webview（`MessageList.tsx`）：运行中的 execute 卡在收到输出时自动展开输出区、自动滚到底部，标题行显示「实时输出」；命令结束后保持展开。补充 `i18n.ts` 英文键。
5. 验证：新增 session-state 单测（增量覆盖、迟到帧保护）；`npm run typecheck`、webview `tsc --noEmit`、定向 vitest；用真实 CLI 跑一条慢命令确认 wire 上有 in_progress 内容；最后用 frontend-tester 逐项验证卡片自动展开/滚动/结束后状态。

不会触碰工作区里已有的未提交改动（Composer 等）。
